AGENTS.md

Working rules for Cadence

These rules express the owner's requested quality constraints for the future project. They do not change instructions in reference repositories.

Product and architecture

  1. Training correctness is the product. Never improve displayed scores by forgiving corrected mistakes, excluding ordinary hesitation, or changing difficulty without recording it.
  2. All application and UI state mutations pass through the engine's typed reducer. Workers return facts; widgets render snapshots. No sibling component mutation, interior-mutable global app state, or worker access to &mut AppState.
  3. Input admission → reduction → presentation preparation → render must not await, perform filesystem/database/network I/O, launch a process, or do corpus-wide work.
  4. Every asynchronous result carries the complete identity and dependency versions it was computed against. Check successful and failed outcomes. Cancellation does not prove freshness.
  5. Headless, replay and live mode call the same reducer and renderer. Fixtures replace effect ports, never product logic. Do not add a demo-only practice path.
  6. Ordered semantic events and durable acknowledgements cannot be silently dropped or coalesced. Only explicitly replaceable notifications/snapshots may coalesce, with their truth retained elsewhere.
  7. Offline means the practice process starts and works with networking disabled, after installing the bundle. All normal history is local.

Rust and maintainability

  • Strong domain types for IDs, generations, revisions, units, positions, counts, probabilities and byte/cell/text lengths. No primitive soup, sentinel numbers, boolean mode combinations or stringly typed events.
  • No naked policy numbers. Named, typed constants or validated policy fields own budgets, timeouts, limits, weights and thresholds; document units and rationale. Arithmetic identities 0/1, enum encodings with a schema, and explicit test examples are fine. Naming MAGIC_500 is not compliance.
  • Checked arithmetic at all external-input/counter boundaries. Generations and revisions never wrap; retire an exhausted slot or stop the operation with a typed error. Saturation is allowed only when clipping is the specified operation, not to conceal lost data.
  • Production libraries return typed errors. anyhow is limited to CLI/xtask aggregation. No unwrap, expect, panic!, unchecked indexing, ignored results, or warning suppression in normal application logic. Unreachable paths need a typed invariant and an explicit reviewable justification.
  • unsafe is forbidden in owned application crates initially. If an unavoidable terminal/platform seam emerges, isolate it in one narrow module with an invariant, safe alternative assessment and tests; do not weaken workspace policy globally.
  • Use cargo fmt --check and Clippy with warnings denied. Review targeted #[expect(..., reason = ...)] only for actual documented false positives; no blanket lint disabling.
  • Aim for modules around 300–400 lines; 600 lines triggers review and decomposition; 800 lines requires an explicit exceptional justification in the same change. Tests count. Generated fixed tables are exempt and carry a generator/provenance link.
  • Split by responsibility, not arbitrary line ranges. Functions with load-bearing branch order should usually become typed state transitions or decision tables.
  • Prefer small concrete interfaces and established dependencies. Do not create a framework, plugin system, home-grown database, CI scheduler, allocator, terminal parser or PRNG.
  • No hot-path full-state serialization, whole-corpus scan, unbounded vectors/channels, per-key SQL transaction or per-key allocation of the entire target text.
  • No compatibility shim left behind when an internal interface changes: migrate every caller and delete the old implementation together. Persisted/wire schema compatibility is explicit and must never be silently dropped.
  • Dependency versions and features are pinned by committed locks. Dependencies must have a named purpose, compatible licensing and documented security/update ownership. Do not use floating latest in qualification recipes.

Verification and evidence

  • Test contracts, behaviours and failure boundaries. Prefer the cheapest layer that exercises the real code. No coverage-percentage target, source-text tests pretending to be behaviour tests, or sleeps as deterministic synchronization.
  • Tests run with an explicit temporary profile; never read/write the owner's real HOME, history or credentials. No network in product gates.
  • Every required formal property has a named production mapping, positive run and negative calibration. Tool absence, parse failure, timeout, skipped proof or zero obligations is a failure/blocked result.
  • Do not substitute a verified toy copy for the function used by the application. Same-source Verus kernels must be called by production. Differential testing is useful evidence, not a universal refinement proof.
  • No assume, admit, sorry, unreviewed external_body, or circular lemma in claimed theorems. List tool/library/OS assumptions and approved trusted adapters.
  • Preserve failing attempts and exact candidate identities. A green cache entry or successful subset is not complete qualification.
  • Docker Compose is the canonical reproducible gate route. Host Rust is optional for iteration. Buildbot schedules the same repository commands; proof/test logic does not live in controller configuration.
  • Do not mutate shared CI infrastructure, disk layouts, public releases or other projects as an incidental fix. Implement the Cadence adapter and report missing shared prerequisites concretely.

Work completion

Maintain a compact status ledger mapping requirement IDs to implementation, tests, proof claims and receipts. Finish all authorised P0–P8 work; do not replace required behaviour with a TODO and describe the feature as complete. Report actual limitations and blocked gates precisely. Human-learning effectiveness is evaluated empirically; software proofs do not certify a guaranteed WPM gain.

Product and daily practice

P-01 Purpose

Tarek wants one terminal-native place to practise every day, including the number row and numpad, with strong accuracy, useful speed gains and automatic familiarity with word patterns. His platform is Linux/WSL with Docker. He uses a Keychron Q6 and a custom top numpad key mapped to Backspace. The actual active keyboard layout is not known; do not assume UK key positions solely from residence.

The first-run experience asks only what affects correct exercises: layout (US/UK QWERTY initially, with a custom text-only fallback), presence of a numpad, and optionally session duration. Defaults otherwise work. All alphabetic keys are available immediately. A brief initial observation period replaces a lengthy beginner unlocking course. Finger guidance is optional and described as a suggestion; the terminal does not observe fingers.

P-02 Fifteen-minute daily plan

The default plan contains 900 seconds of allocated session time:

Phase Seconds Purpose
Warm-up 60 Familiar words at an easy pace; timing-quality check
Adaptive words 300 Weak transitions/words, due review and unfamiliar vocabulary
Number row 120 Digit reaches in text and neutral identifier contexts
Numpad 180 Digit sequences, decimals, zero, corrections and entry submission
Prose transfer 180 Natural sentences with matched punctuation difficulty
Review 60 Three useful findings and the next session's focus

Typing allocations total 840 seconds; review totals 60. Transition screens do not add mandatory exercises. Pause, explicit instruction reading and interruption may lengthen wall time; the app must label active time versus elapsed time honestly. Review can be dismissed immediately. At a phase deadline, end the scored slice at that event boundary, retain the partial exercise, and offer the next phase; do not force a final long word or add hidden overtime. A partial word contributes observed characters and accuracy but not a completed-word success.

The plan freezes policy, layout, corpus identity and initial learner revision. Text for the current exercise is immutable. Generate the next exercise ahead of time using committed or explicitly provisional local observations; each accepted exercise records its own basis. If preparation is late, show a brief preparing state or use an explicitly recorded safe fallback corpus block. Never block input on a planner task.

Changing duration creates a new plan at the next session boundary. For 5–30 minute presets, allocate an exact integer budget using documented phase minimums and largest-remainder apportionment. A 5-minute session still includes both numeric tracks unless the user explicitly disables one. Reject an impossible custom configuration; do not quietly remove a selected track. Proof obligations cover the allocation algorithm, not the educational optimality of these durations.

P-03 Initial and ongoing adaptation

First session: common real words and short neutral prose, then simple numeric sequences. Do not infer speed targets from other users. Until enough clean observations exist, sample broadly and explain “building your baseline.” Warm-up timing is recorded separately from core progress. Every enabled track gets exposure; a weak numpad does not reduce main-keyboard difficulty.

Daily sessions mix difficult material with familiar material, avoid exhaustion loops, and let the user pause or stop without losing completed work. Returning after a break increases review exposure within the same time budget rather than issuing a backlog demand. The scheduler proposes a session, not a compulsory debt list.

Benchmark: once per seven completed daily sessions, replace the first 120 seconds of the prose phase with a standardized unseen-text probe, leaving 60 seconds for normal prose. Match punctuation, capitalization, word-length/frequency strata and duration to the previous comparable probe. Keep passages unique for the profile. Mark practice on a benchmark passage as contamination and retire it from future benchmark use. Interrupted or pasted-input probes are retained but excluded from the comparable benchmark series. The UI must say when there is not enough comparable evidence.

Numeric transfer: use fresh amounts/sequences from the same generator class, never the identical list every day. Track clean-entry rate and numeric throughput independently. Do not compare a decimals drill to an integers drill as a single speed trend.

P-04 Corpus and modes

Mandatory first release: adaptive real words, natural prose, number row, numpad and user-selected single-track practice. Add Rust/shell and explicit local text import before final P8 qualification; these are requested scope, not an excuse to block the first working slice.

The main word pack targets at least 20,000 distinct vetted English surface forms in the shipped release, with an expansion target around 50,000 when quality/licensing permit. “All words” means broad, expandable coverage, not a claim to include every dictionary entry. Frequency bands must keep everyday words prominent while sampling the long tail. Do not manufacture size by counting capitalization variants, duplicates, arbitrary identifiers or inflections the source does not support. Record exact counts, normalization and source licences. If suitable content cannot be licensed, mark the corpus gate blocked rather than ship ten words and claim completion.

Prose must be natural, edited and usable offline. Use licensed/public-domain material or purpose-written passages; inspect readability, unfamiliar proper nouns, archaic wording and punctuation. The handover contains examples, not the release corpus. Rust/shell snippets should be short, plausible and non-executing. Imported snippets are never executed, evaluated or sent elsewhere.

Numpad content covers digits 0–9, repetition, alternation, integer/decimal amounts and Enter; add + - * / in a selectable operator drill. Preserve string identity: 005.20 must remain exactly that string, never be converted to the number 5.2. Start with decimal point; alternate separators are explicit pack/profile settings. Number-row symbols follow the configured layout.

P-05 Boundaries

No accounts, cloud synchronization, leaderboard, multiplayer, social features, subscriptions, AI coaching API, background keylogger or automatic repository scanning. These are not needed for the authorised product. No forced streak guilt or constant score animation. Themes are meaningful but secondary: ship dark, light and terminal-default palettes; custom semantic-role palettes are small configuration data.

Measure progress through accuracy and transfer, not daily badges. Explain uncertainty and lack of data. Target thresholds and the 15-minute mix are tunable product hypotheses. The app cannot promise that 15 minutes is globally optimal or that a specific speed gain is guaranteed.

docs/02-learning.md

Learning, scoring and the adaptive planner

L-01 Three separate objects

  1. Observation ledger: what was displayed, what input arrived, when it arrived, and what was corrected. Historical facts are immutable once committed.
  2. Learner model: derived error/timing/review summaries by skill key. It can be rebuilt or migrated without editing observations.
  3. Planner policy: versioned decisions about what to practise next. Policy changes do not rewrite old scores.

SkillKey includes track, layout revision, content class and pattern identity. Numpad 12 and number-row 12 are different skills even when the terminal reports the same characters. Annotate physical-source evidence as VerifiedKeypad, VerifiedMain, or Unverified; do not infer it from content. Symbols/case and code/prose retain separate comparability metadata.

L-02 Input and scoring semantics

V1 training alphabet: printable ASCII, explicit newline, and £ where the chosen layout supports it. Imported prose may opt into a documented typography-to-ASCII normalization (smart quotes, em/en dashes and non-breaking spaces); show a preview and preserve the original. Code defaults to exact bytes within the supported UTF-8 alphabet. Reject unsupported training characters before a scored session with line/column diagnostics. UI text itself remains Unicode-aware; this limited training alphabet avoids pretending IME composition has single-keystroke timing. Wider language/input support is a future contract change.

TextUnitIndex identifies an expected logical training unit, not a UTF-8 byte or terminal cell. One ASCII character/£/newline is one unit. Wraps introduced by the renderer do not become expected input. In ordinary word/prose practice, edit only at the tail: append and Backspace (optional explicit delete-current-word); arrows never reposition the typing caret. This makes alignment unambiguous. Mistyped input advances the attempted position and remains highlighted; correct it with Backspace. Do not silently skip a wrong character or automatically resynchronize on a space.

The target is immutable for an exercise. Maintain:

  • first_outcome[position]: Option<Correct | Incorrect>: assigned on the first content insertion at that expected position and never replaced.
  • attempt_count, correct_attempt_count, deletion_count, overflow_attempt_count: cumulative event facts.
  • A bounded current typed buffer, and a committed frontier of already completed exercises.
  • Per-word/entry flags for any error, deletion, interruption or paste in that attempt.

First-pass accuracy = first-correct positions / first-attempted expected positions. A later correction never changes either historical position outcome. Deleting a correct character and retyping incorrectly leaves that first outcome correct, but reduces attempt accuracy and marks the word non-clean. Show attempt accuracy in detailed results so this distinction is visible. Attempt accuracy = correct content insertions / all content insertions, including overflow. Backspace is a correction event, not a content insertion in that denominator. Never average per-exercise percentages: aggregate numerators and denominators.

Example target cat, input c x Backspace a t: first-pass = 2/3; attempt accuracy = 3/4; one deletion; current buffer exact; clean-word false. A successful correction is useful behaviour, but it is not an error-free first attempt. If the user abandons after c x, first-pass is 1/2 and no completed word is awarded. Restart creates a new attempt linked to the abandoned one; it does not delete the prior facts or grant a clean spaced review.

Content beyond the target length has no expected slot, counts as incorrect attempt/overflow, and prevents completion until deleted. Buffer length is bounded by target units plus a named extra-input allowance. Exceeding that bound visibly rejects further content and marks measurement interrupted; never silently discard keys while claiming an ordinary score. Empty attempts and zero-duration observations yield None, not infinity, 0% accuracy, or a made-up baseline.

Correct WPM = correct_visible_or_committed_units × 60 / (5 × active_seconds). Correct units at an unfinished slice are positionally matching units, not all keys pressed. Completed slices retain their contribution exactly once. Editing/repeating does not increase the numerator. Spaces, punctuation and explicit newlines are units; renderer line wraps and submit-only numpad Enter are not. Use exact rational/count-duration arithmetic internally; format at the UI edge. The conventional five-unit definition belongs in one named constant.

Numpad: correct digits/min counts matching digits only; decimal/operator units contribute to accuracy, not the digit numerator. Exact-entry rate measures submitted exact strings (useful in free-flow assessments). Clean-entry rate measures entries that were exact without any error/deletion in their first attempt (the primary numeric precision measure). In correction-required drills, exact submitted entries will normally be 100%; do not present that as evidence of improved first-pass skill. Enter submits only; it must not auto-advance a wrong value. Leading zeros and decimal places are significant.

Expected-pattern observations are anchored to target positions. A bigram/trigram occurrence is first-correct only if all constituent expected positions were first-correct; it is counted once when its final position is first attempted. Re-typing an occurrence does not add a new training success. Overlapping patterns may each get one observation, but the overall accuracy ledger still counts positions once. Word observations require a completed boundary; incomplete words are retained as partial evidence only. Keep error and timing evidence denominators separate.

L-03 Time and measurement quality

Use MonoTick (checked microseconds since the run's timing origin) for intra-run timing and injected UTC/calendar values for review scheduling. Stamp terminal input when read at ingress, before the engine queue. Record reducer consumption order separately. This measures terminal-to-app arrival, not electrical switch actuation. Input from a stalled pipe, paste, recorded macro or invalid ordering cannot produce credible physical cadence evidence.

The stage clock starts on the first valid content key, stops at its allocated deadline, and excludes only explicit pause intervals. Ordinary reading/thinking/hesitation remains in active time. No silent trimming of long gaps. Focus loss may pause when the terminal actually reports it; unavailable focus reporting is not fabricated. Any paused or interrupted benchmark is ineligible for comparison, though its results remain visible. Manual practice can show active WPM with a pause label. On crash/restart, a resumed exercise is an interrupted new timing segment; never subtract wall-clock downtime from a claimed uninterrupted trial.

Inter-key intervals for model timing use adjacent first-attempt, correct content input within a contiguous clean segment. Exclude pairs crossing a correction, pause, service interruption, paste, stage/exercise boundary or known transport degradation. Keep word-start latency separate from within-word transitions. Do not divide a word's total duration evenly among its keys. Reject negative/backward timestamps; equal timestamps are possible at the transport and must not create infinite speed. Count them as insufficient timing resolution. Store named reasons for excluded timing samples.

For resource overload, loss of ingress ordering, a gap in sequence numbering, or a corrupt trace, pause/unqualify measurement rather than produce a normal score. Auto-repeat events are ignored as held-key repeats when reliably identified; do not classify repeated-letter words as repeats on legacy terminals where no distinction is available. Bracketed paste is rejected in practice and cannot become keystroke evidence. Explicit headless scripted input is tagged synthetic and stored only in its sandbox profile.

L-04 Statistical model: transparent and conservative

V1 uses a bounded rolling observation window per skill (last 128 valid occurrences with contributing session/day identities), all-time aggregate counts, and robust recent timing summaries. This window is a policy choice, not a published optimum. Unit, bigram, trigram and frequent whole-word models share the same evidence rules. Do not instantiate a dense Cartesian product of all possible words/patterns.

Error estimate: Beta(1,19) prior for error probability, with posterior mean (recent_errors + 1) / (recent_observations + 20). This smooths sparse estimates. It is not an independently validated psychological model. Mark evidence “sparse” below 20 observations or fewer than two separate sessions; show counts, not a spurious precise confidence percentage. Shrink sparse whole-word timing toward its constituent pattern class and fall back to broad sampling. Unknown does not mean mastered.

Timing: median and interquartile range of valid within-class intervals; no unstable global mean from a few samples. Derive a hesitation score relative to the user's clean timing in the same track and comparable transition class. Do not demand the same latency for every key reach. Lack of sufficient clean timing means no timing score, with weights re-normalized over available evidence. A slow unfamiliar word can reflect reading/planning as well as motor skill; explanations must not diagnose finger or cognitive causes.

Candidate utility is bounded fixed-point arithmetic (BasisPoints, 0..10,000). Initial weights in policies/trainer-v1.toml: error 5,000; hesitation 2,500; relevance 1,500; exploration/uncertainty 1,000. Weighted sum divided by the sum of available weights is in range; no floating NaN/order instability. Relevance comes from corpus frequency and explicit pack selection, never hidden monitoring of the user's work. The score ranks within a lane, while lane quotas protect review and breadth. Preserve the score components and a reason code for explanation.

No estimate or coefficient is a guaranteed optimal learning algorithm. Include a policy-comparison mode in developer simulations: fixed mixed practice versus adaptive practice on synthetic learner models. This detects pathological allocation, not human efficacy. Actual effectiveness is judged through repeated comparable transfer probes and the owner's experience.

L-05 Selection lanes and termination

Adaptive words use blocks of 10 scheduled word slots: 6 targeted, 2 due review, 2 breadth. A fixed interleaved lane order is [target, broad, target, review, target, target, broad, target, review, target]. Prefixes therefore remain mixed when the stage ends mid-block. A focus unit may own at most 3 targeted slots per block. An exact word may appear at most twice per block and at most twice consecutively, allowing a short useful repetition without a drill trap. Incidental occurrences of that unit elsewhere are not claimed to satisfy this exposure cap; the cap governs the planned focus label.

Review takes the oldest continuously eligible item from a FIFO due-admission queue. Admission order is monotonic when an item first becomes due; a newly imported overdue item joins at the tail rather than jumping ahead. An item cannot be queued twice. Following review, remove it and compute its next due date. Paused/disabled tracks preserve their queue but have no service guarantee while disabled. A bounded backlog must expose a diagnostic if at capacity; never silently drop review work. Review is a budgeted opportunity, not a demand to clear all due items today.

For each slot, query indexed eligible candidates, bounded to 256 materialized entries. The bounded scan selects the highest utility eligible candidate with seeded tie-breaking. Use an established pinned deterministic PRNG and record its algorithm/version/seed; never depend on HashMap iteration. The same inputs produce the same plan on supported builds. Category and word/focus eligibility checks are shared functions, not duplicated per lane.

Fallback order is explicit: targeted → due-review → breadth; due-review → breadth → targeted; breadth → due-review → targeted. Keep repetition/cap/content safety constraints during fallback. A tiny corpus with no legal candidate returns NoEligibleCandidate, with a plain explanation and an offer to broaden content. No unbounded resampling loop, hidden constraint relaxation or arithmetic divide-by-zero. The release corpus must pass an offline capacity check for all default lane configurations.

Fairness claim is limited and precise: when due work is continuously eligible and at least one review slot is served per block, a queued item with q eligible predecessors is served within at most q+1 served review slots, assuming no insertion ahead, completion of those slots and bounded worker progress. Two reserved slots per full block sharpen the block bound. Do not claim finite-time coverage of every word in an expanding corpus; breadth is a lane quota, not a guarantee that random selection visits every item.

L-06 Review and pace policy

Review intervals begin at 1, 3, 7, 14 and 30 local-calendar days. Two clean completions on different sessions/days are required before promoting an item beyond its current interval. Same-session repetitions count as practice, not independent retention checks. An error returns the item to the 1-day level; it may get one short reinforcement later in the current session, within repetition caps. Timing alone never labels a word forgotten. Check additions for overflow and record calendar/timezone identity; wall-clock rollback cannot make all items instantly overdue or grant future success.

Default desired first-pass accuracy is 98%. Pace is a soft goal, not a moving forced cursor. Raise a track's suggested target by at most 3% after three qualifying blocks across at least two sessions, each with at least 100 first-attempt positions and accuracy at/above the threshold. Also require no material attempt-accuracy degradation. A block below 95% lowers the suggested target by up to 5% and increases familiar practice within targeted slots. Values between bands keep the pace steady. Insufficient evidence keeps the current target. The initial target is the robust baseline of clean samples; it is absent until known. Bounds and hysteresis belong in policy, with integer-rational comparisons tested at equality boundaries.

No progression inference crosses layout changes, incompatible corpus difficulty classes, paused benchmarks or synthetic sessions. A theme change does not reset learning. A changed layout starts a separate profile partition while preserving earlier history. A minor display fix never silently becomes a new scoring version.

L-07 Required correctness properties

Scoring: first outcomes are write-once; counters are bounded; corrections cannot improve old first-pass accuracy; completed contributions are committed once; fractional aggregation is exact; timing exclusions are explicit.

Planner: exact time budget, legal candidates only, fixed finite selection work, deterministic replay, lane quotas when feasible, explicit failure when infeasible, repetition/focus bounds, no duplicate due entries, and fairness under stated eligibility assumptions.

Progress: observations retain policy/corpus/layout/measurement identity; benchmark trends compare like-for-like; inability to prove comparability displays an unavailable comparison. These software properties are the subject of tests/formal work. Human learning benefit is not a theorem in this project.

Architecture, asynchronous updates and protocols

A-01 Workspace boundaries

Dependencies: core has no workspace dependency; trainer → core; engine → core/trainer; data → core/trainer and engine port DTOs if necessary; tui → engine/core; runtime → engine/data/core/trainer; driver → engine/runtime/tui/core; binary → runtime/driver/tui/data. No reverse edge from engine into runtime/tui/driver. Prefer port types in core/engine over a shared “utils” dumping ground. These are ownership boundaries; split modules inside them before inventing additional micro-crates.

The engine's public mutation API is conceptually reduce(&mut self, envelope: EventEnvelope) -> Transition. Transition contains bounded owned effects, dirty/presentation information and domain outcomes. Internal subsystem mutation remains private to the owner. Snapshot/view preparation is an explicit engine operation; Ratatui paint receives &PreparedView and immutable theme data. Paint cannot correct scroll state, initiate I/O, alter counters or advance time. Layout-dependent state changes are explicit ViewportChanged/preparation events before paint.

A-02 UI bus and ownership

Terminal adapter → typed input envelope → sequenced event admission → engine reducer → prepared view → renderer. Async effects → bounded workers → immutable completion envelope → same event admission/reducer.

There is one owner thread for app state. Widgets return typed UiIntents (such as StartDailyPlan, Pause, SetTheme) through command dispatch. Children never mutate parents/siblings. Arc<Mutex<AppState>> is forbidden. Share immutable corpus/model snapshots with workers; only the owner accepts/replaces them. A background database writer can be single-threaded with its own state; it never mutates the app state directly.

Keep input reduction synchronous and bounded. Preparation may copy cheap IDs/visible spans but not serialize the whole profile. Large trend calculation, corpus indexing, database work and plan candidate retrieval use workers. Rendering may skip obsolete frames, but logical input transitions and effects remain complete.

Async does not require putting a general Tokio executor around every object. A small bounded worker pool plus channels is sufficient for this offline workload. Use established channel primitives. If Tokio is selected, blocking SQL and file work stays on bounded blocking workers; the engine still has no async fn API.

A-03 Typed identity and freshness

At minimum: ProfileId, SessionId, ExerciseId, WordId, JobId, ViewId { slot, generation }, SessionEpoch, RequestRevision, LearnerRevision, CorpusVersion, PolicyVersion, LayoutRevision, EventSeq, CommitSeq, FrameRevision, MonoTick, UtcDay, TextUnitIndex, CellColumn, TerminalRows, BasisPoints.

Use existing generational slot storage for ephemeral views/jobs, with typed wrappers. Persistent IDs are stable IDs; generations are not database row identities. Generation exhaustion retires a slot; no wraparound/reuse. An absent/deleted owner invalidates all of its pending view work. Cancelling a job is best effort; a late success or late failure still goes through admission.

An async result envelope records job_id, owner key, request kind/revision, and the dependencies appropriate to that result. The acceptance predicate is an explicit pure function for that result domain. Examples:

  • Next-exercise candidate: session ID + session epoch + next-exercise request revision + requested learner revision + corpus/policy/layout versions.
  • Progress query: profile ID + query revision + database snapshot watermark + filters; a view generation only governs whether it can paint that view.
  • Save acknowledgement: profile/session + commit sequence + payload digest. It is independent of whether the original practice screen still exists.
  • Theme preparation: theme request revision + view/display configuration revision, not the learner revision.

Do not compare every result against a global revision incremented by every keystroke: that can make useful background work permanently stale. Use immutable admitted planning bases. If the relevant learner basis changes before delivery, either supersede that request once or accept the snapshot under an explicitly frozen exercise plan; document the choice. V1 freezes a next-exercise request's learner basis until consumed, unless the session/policy/layout/corpus changes. In-session observation updates do not invalidate that already requested exercise; the following request uses the newer model.

Accept only a result with the matching pending JobId and complete key. Consuming removes that pending request, so duplicate completions cannot apply twice. Record rejected deliveries in a full debug trace for replay. An old failure must not replace the current success with an error banner.

A-04 Bounded transport without lost completion facts

V1 suggested named limits: input FIFO 1,024 events / 256 KiB; at most 8 outstanding worker jobs; at most 4 MiB per completion payload; 32 MiB total retained completion payload; 64 input events per owner turn; 4 ms owner-turn budget. These are starting resource policies, not naked literals or proven optimal settings. A corpus-load result holds an immutable bounded handle/summary rather than sending 50,000 copied rows through the bus.

Worker lifecycle uses reserved result slots in a bounded JobRegistry. Reserve a slot before launching. Each slot holds one terminal outcome until the owner consumes it. Worker publication signals a coalescible wake hint; the outcome remains in the slot even if wakes merge. A wake is not the completion record. Cancellation requests do not release the slot before terminal acknowledgement/join. The result slot cannot be overwritten by another job or recycled under the old generation.

Input is ordered and semantic: never coalesce keys, paste, pause, stage-boundary actions, errors or save acknowledgements. Terminal producer backpressure is permitted off the owner thread, but backlog/latency thresholds must invalidate affected timing samples and visibly pause training if fidelity can no longer be guaranteed. Do not keep reporting reliable IKI while a producer is blocked behind a saturated queue. Bound input payloads before admission.

The owner never blocks sending effects to a full work queue. It keeps a bounded pending intent with an explicit Busy/Preparing presentation, or refuses a new user operation before claiming it started. Critical save intents have reserved/coalescible cumulative checkpoint storage so a planner task cannot starve persistence. Full checkpoints may supersede earlier unlaunched checkpoints only because they contain the full cumulative session state and monotonic sequence; transaction idempotency rules still apply. Never coalesce already-dispatched writes or their receipts.

Each turn services input plus ready results with a documented bounded round-robin policy, then prepares/renders when dirty or when a visible timer boundary requires it. Continuous input cannot starve save acks and completions; continuous results cannot starve input. Idle waits block on channel readiness. Timer/redraw hints may coalesce; explicit elapsed time is sampled and recorded at reduction, so a dropped tick cannot change the phase budget.

A-05 Session lifecycle

States: Ready, Running, Paused, PhaseComplete, Review, Finishing, Saved, SaveFailed, Aborted.

Start freezes the plan and policy identity. First content input starts that phase's active clock. Pause records a clock boundary before changing state. Resume uses a fresh contiguous timing segment. Phase timeout consumes only events whose admitted timestamp is within the phase boundary; ties use the documented order: keys at the exact deadline are outside the scored slice. The input adapter must not let an earlier timestamp arrive after a later admitted one; reject backward time as measurement-invalid.

Finishing requests a final durable checkpoint and continues rendering a “saving” state. Only a matching final commit receipt enables Saved. If the user exits while a save is pending, try a bounded flush; on failure retain/recover the last acknowledged state and return an explicit non-success outcome. Never label an unacknowledged write saved. Data errors remain visible and retryable; do not discard the session just to exit cleanly.

A-06 Persistence protocol

The engine issues cumulative session checkpoints with monotonic CommitSeq and content digest. A single database writer serializes commits. In one SQL transaction: validate session/profile identity and sequence, insert immutable new event chunks, update the cumulative session record and derived learner watermark, and store the commit receipt. Any duplicate (SessionId, CommitSeq, digest) returns the prior receipt. Same sequence with another digest is corruption/conflict. A stale sequence cannot regress current state; a later cumulative checkpoint may cover an earlier one only after validating its prefix digest/event continuity.

Commit acknowledgement is emitted after transaction success. A lost acknowledgement followed by a retry must not double-count errors, successes or review scheduling. On reopen, load the database receipt/watermark and expose recovered state without applying already committed deltas again. Updates are cumulative or explicit event-derived transitions, never blindly additive retry payloads.

No cross-process shared mutable session. Acquire an advisory writer lock before opening the writable profile; a second interactive writer fails clearly or opens an explicitly read-only progress view. A live lockfile's presence is not proof of ownership; use OS locks, not PID-file polling. Read-only queries use consistent snapshots.

A-07 Trace and replay

A versioned trace header records build/scoring/policy/corpus/layout identities, start state or its fixture identity, clock origin, seed and capability evidence. Record external events before acceptance, including stale/failed responses, alongside reducer-consumption sequence and deterministic effect requests. Checkpoint observations carry state hashes; optional frame nodes carry canonical cell grids/cursor/style hashes. Time/randomness are inputs, not sampled inside pure functions.

Replay uses the same reducer and renderer with real effect execution disabled. It verifies effect requests and consumes recorded completions. Unexpected side effect, event gap, incompatible version, inconsistent digest, truncated trace or observation divergence is an error. Report the first diverging event and compact state/cell diff. Read-only replay must never write to the real profile or rerun imports.

Full replay traces containing typed/imported text are explicit opt-in debug exports. Default logs are bounded and omit raw text. A redacted trace is labelled non-replayable when required content is absent; never claim forensic replay from hashes alone. A synthetic fixture trace can always include its synthetic text.

U-03 Key ownership

In menus, arrows/Tab/Enter navigate; q quits and ? opens help only outside text entry. During practice, all printable characters including q, ?, :, / and digits are training input. Esc pauses and opens practice controls; another Esc resumes if safe. Ctrl-C follows a documented quit/flush path; it must not be a printable training character. Function-key navigation must pause before leaving active practice. Do not steal Tab/Enter from a code exercise where explicitly expected; command dispatch depends on the active input owner.

Backspace deletes one logical training unit; the physical Q6 remap is simply another Backspace event. A delete-word binding, if present, is one explicit action with a counted deletion range; it does not erase first outcomes. No invisible autocorrection. A paste is one classified paste event, never a simulated typed sequence.

Bindings are described once in typed command metadata used for dispatch, help, footer hints and headless action validation. Unknown/unavailable bindings must not appear as working shortcuts. Default mouse support can select buttons/settings, but every action is keyboard accessible.

U-04 Settings

User-facing settings are limited to choices with a meaningful effect:

  • Duration (5/10/15/20/30 minutes), enabled tracks and relative track emphasis.
  • Active keyboard layout; numpad availability and decimal separator.
  • Accuracy target within validated bounds; live pace on/off; strict correction versus flow assessment where supported. Strict correction is the default practice mode.
  • Word frequency breadth, punctuation/capitalization level, explicit content packs, Rust/shell optionality.
  • Theme, optional key guide, high-contrast mode and animation off/on (off by default).
  • Explicit import/export/backup paths and opt-in content trace recording.

Do not expose every statistical coefficient or queue limit as a casual UI slider. Those belong in versioned trainer/runtime policies and diagnostics. A settings page can show effective values and provenance. All values are typed/validated; unknown keys or invalid values report the location and expected range. Partial configuration applies defaults to omitted fields, never to invalid supplied values.

Precedence: built-in defaults → explicit user config → CLI overrides. Relative XDG environment variables are ignored as invalid according to the XDG specification. Profile-dir overrides make test/headless isolation easy. Document layout/content compatibility; changing a score-affecting setting takes effect next exercise/session as specified, never halfway through a target. Theme/display changes can apply immediately through the reducer and do not reset learning.

In-app settings write config atomically through the data worker, with source version/digest checks to avoid clobbering an externally edited file. Preserve comments if using a TOML editing library. U-05 Results and explanations

After a block: one concise observation, one next action and relevant numbers. H-02 NDJSON protocol v1

Each line is one UTF-8 JSON request, maximum 1 MiB. Envelope: v:1, id as a decimal string representing a positive bounded u64, op, args, and optional expected_state_revision as a decimal string. JSON integers for dimensions/small durations must be checked; u64 IDs/revisions stay strings to avoid JavaScript precision loss. Unknown operations/fields, invalid enum values, unsupported versions, oversized lines and malformed JSON fail with stable codes and no state mutation.

Requests are processed in stream order. IDs strictly increase for new requests. Keep a bounded response cache of 1,024 completed requests, keyed by ID and canonical request digest. Repeating the same ID and same request returns its original result without another mutation. Same ID/different request returns RequestIdConflict; an old evicted ID returns RequestExpired, never re-executes. Malformed envelopes without a usable ID get a protocol error and no cache mutation. Reconnect creates a new stream scope; replay/trace identity is separate. This is not an exactly-once distributed network RPC claim.

Response: {v,id,ok,result} or {v,id,ok:false,error:{code,message,details}}. Successful results include state_revision, event_seq and (when relevant) durable_commit_seq, all strings. ok means the requested synchronous operation was applied/validated; it does not imply async jobs or persistence completed. stdout contains protocol records only; stderr contains bounded diagnostics. Machine consumption must not parse decorative CLI output.

H-03 Barrier semantics

Two scopes:

  • causal: captures all work caused by requests through a specified event sequence, including descendants spawned when their completions are consumed. It completes when those jobs/results/pending dispatches are drained. It excludes later unrelated actions and periodic UI clocks.
  • durable: includes the causal scope and requests/awaits a checkpoint covering the captured session watermark. The result identifies that watermark. A later queued key is not accidentally declared persisted.

Every effect gets an origin/causal group inherited by follow-ups. Jobs stay outstanding through cancellation acknowledgement and result consumption, not merely until a worker computes a value. Register child work before marking its parent drained. A barrier must not return in the gap between a parent completion and child registration. Virtual mode pumps deterministic service deliveries; it does not sleep until “the screen seems quiet.” Native mode waits on actual completion signals with a bounded watchdog and returns pending job IDs on timeout.

Reject through_event_seq beyond the latest admitted event, or outside this driver session. Event sequence zero denotes the initial state. Barrier observation does not advance virtual practice time; watchdog time is a separate wall-clock safety bound. A durable barrier explicitly admits its checkpoint request and includes that request in its own scope.

Limit each request to one active barrier in the sequential v1 driver; this avoids speculative concurrent RPC complexity. Control/read streams continue only as explicitly allowed. A fixture barrier with undelivered jobs fails with their IDs at its watchdog bound rather than silently auto-succeeding. The “auto” fixture service policy, where enabled for ordinary examples, deterministically produces registered fixture results and is recorded in hello.

H-04 Captures and replay diagnostics

docs/07-assurance.md

Formal assurance with honest scope

V-01 Tool choice

Use TLA+ to specify interleaving-sensitive protocols; TLC to explore bounded state spaces and kill deliberate faults; TLAPS for general inductive safety arguments; Verus for selected executable Rust algorithms and their arithmetic/collection invariants. This follows the inspected Strop approach and avoids maintaining a separate Lean implementation of Rust algorithms merely to prove the copy.

Verus is an SMT-based program verifier with a different trusted toolchain from Lean; this document does not claim identical foundational guarantees. Its advantage here is proof of the functions the application actually calls. Keep the verified surface small enough to complete. Lean remains an option only if a concrete mathematical claim cannot be expressed sensibly in the selected stack; it is not a mandatory extra dependency.

Formal claims prove stated software properties under assumptions. They do not prove human learning benefit, arbitrary terminal fidelity, absence of every Rust bug, SQLite/OS durability, or the compiler/hardware stack. A successful finite TLC run is not an unbounded theorem. A verified predicate alone does not prove every caller supplies the right identity.

V-04 Planner proof shape

Budget: take validated nonnegative minimum allocations whose sum is ≤ budget. Allocate the remaining integer seconds by quotient/remainder against positive integer weights. The sum of floors is ≤ remaining budget; the unallocated remainder is less than the count of positive-weight phases. Add one second to that many phases in descending fractional remainder, stable phase-ID order on ties. Prove exact sum, minimum preservation, no overflow and determinism. Validate all sums/products before fixed-width execution; a proof over mathematical integers alone is not sufficient for u64 code.

Selection: preconditions bound candidate vector length and ensure candidate records/utility inputs are validated. A scan invariant says the current best, if any, is eligible and at least as good as every previously visited eligible candidate under the total (utility, seeded_tiebreak, stable_id) order. Loop index strictly advances and is bounded by vector length. At exit return the best or an explicit no-candidate result. This proves optimality only within the materialized candidate vector, not across all English vocabulary.

Quotas/caps: each successful slot consumes one unit from its requested/effective lane counter and updates the selected word/focus counts once. Prove count bounds and consistency between emitted slots and counters. Infeasible fallback returns a tagged decision; it cannot rewrite the requested lane and then claim the original quota was fulfilled. Claim exact 6/2/2 only for complete feasible blocks; retain short prefixes and fallback explanations truthfully.

Due fairness: for a fixed continuously eligible item, rank is the number of eligible queued predecessors. A review service removes a predecessor or the item; no new admission increases this rank because admission is tail-only. Repeated successful service therefore reaches the item in at most rank+1 review services. Calendar time requires additional assumptions about enabled tracks and sessions actually being completed; users can stop practising indefinitely. Record these assumptions in the theorem rather than claiming unconditional daily fairness.

Scoring: prove append assigns only previously empty first-outcome slots; deletion changes the visible buffer and correction counts but leaves the first-outcome vector unchanged. Prefix-extension can improve the overall ratio by adding new correct positions, so the actual theorem is “correction alone cannot erase prior first-attempt errors,” not “accuracy can never rise.” Bind committed exercise IDs to a consumed set or monotonic frontier to prevent duplicate cumulative contribution.

V-05 Production linkage and negative calibration

Place verified functions in the owned production modules, compiled as ordinary executable Rust after ghost erasure. Both Verus and normal builds consume exactly those source files. Verify their callers' precondition establishment by types/runtime validation/tests, and formally where practical. The claim manifest records symbol paths, source digests, verifier command/toolchain/solver, theorem names, assumptions, calibration mutants and runtime correspondence fixtures. A function name or comment alone is not a link.

Keep mutants outside shipping code or behind a test-only build configuration whose absence is checked in release. Required examples: ignore epoch; accept consumed request; discard a full result slot; ack before commit; add a retry twice; return a barrier before child registration; clear first-error on Backspace; allow a repeated word past cap; off-by-one budget remainder; starvation through insertion at the head of review.

A model mutant passes calibration only when the expected named invariant/temporal property fails with a valid counterexample, not on any nonzero tool exit. A Verus mutant must invalidate its intended contract; an actual-code mutant must be killed by the named test. Parser errors, missing tools and arbitrary crashes are gate failures, not successful mutation kills. Keep bounded search details and model assumptions in receipts.

V-06 Practical gate discipline

Separate fast unit/headless feedback from heavier model/proof qualification. Run affected formal lanes while implementing their modules, not after the UI is complete. A private experimental binary may be used for feedback, explicitly unqualified. The final owner bundle requires all declared proof rows; no optional “formal later” switch in the default qualification profile.

Do not add a giant theorem about the whole TUI. Small protocols and real algorithm kernels are valuable if linked to the production path. Track unproved assumptions transparently. An exhausted proof budget is a blocked obligation to refine, not permission to redefine a required theorem as a test.

4. Owned workers: what the owner actually maintains

An owned worker is a machine/environment under the owner's administration running a small worker service, plus the required build tools, workspace/cache storage, and resource limits. It need not be a rented server or a separate physical machine.

Maintenance consists of:

  • Service startup/reconnection and controlled shutdown.
  • Pinned build environments and deliberate updates, separate from emergency host security maintenance.
  • Disk/cache quotas, usable memory, and bounded concurrency.
  • Clean workspaces and isolation from personal credentials/data.
  • Controller database/configuration and promoted artifact backups.
  • Periodic restore and reconnect checks.

There is no obligation to provide enterprise uptime. A sleeping or rebooting worker may delay work; it must not cause missing gates to become green.

Initial placement after the macOS decision

  • Controller: this workstation's WSL environment, using a dedicated controller account and private state. Start with SQLite for a small single-controller deployment; use a supported backup procedure, not an arbitrary copy of a live database.
  • Linux x86_64 worker: the same physical workstation, in a dedicated CI environment/account with bounded access. Prefer its own Docker engine in a CI distro/VM over unrestricted use of the owner's general-purpose Docker Desktop daemon.
  • Mac Studio: not part of the required setup. No macOS worker, Remote Login, VPN enrollment, or sleep-policy change is needed for the now-removed target.
  • Native Linux ARM64: remains a separate capability if retained. An ARM64 Linux VM on the Mac Studio is an optional way to supply Linux-on-ARM execution without supporting macOS as a product target, but it requires deliberate setup and qualification. It is not assumed available or automatically included in this rollout.
  • Strop native Windows: the Windows host is a possible future worker, not already-qualified Windows evidence. A Linux worker under WSL does not replace Windows/MSVC, native input, GUI, WSL-discovery, or hardware-specific checks.

A separate WSL distro/user reduces accidental contamination; it is not a hostile-code security boundary equivalent to a separate machine. WSL distributions and Windows integration share host trust. Do not run unreviewed public-fork code on this workstation. Keep the controller's private state inaccessible to worker accounts; never mount it into build containers.

If the pilot uses the existing Docker Desktop daemon, label it a trusted-code, non-publishing pilot. Docker access is privileged access. Do not run broad container/volume cleanup or let jobs access unrelated personal containers.

5. WSL qualification and availability boundary

WSL2 is a real Linux kernel environment and can be a useful x86_64 Linux worker. The existing Docker-first commands are a good starting point, but each required feature must be exercised before admitting the worker.

  • Keep checkouts, scratch homes, permission fixtures, caches, and filesystem-fault fixtures on Linux-native storage, not /mnt/c, SMB, or another Windows-backed filesystem.
  • With Docker Desktop, record the actual test container mount/filesystem and daemon host, not only the filesystem of the source checkout. A bind mount/export path can have a different behavior from an in-container native volume.
  • Exercise the actual confinement prerequisites, namespaces, seccomp/capability behavior, process supervision, SSH/PTY behavior, and Docker/BuildKit provider behavior used by each repository.
  • Label the receipts with WSL kernel, Docker Desktop/engine version, container image digest, architecture, filesystem/mount type, and granted capabilities.
  • Software fault injection and process-crash tests remain those kinds of evidence. They do not establish bare-metal power-loss behavior, arbitrary filesystems, native systemd-manager equivalence, or KVM/nested-virtualization capability.
  • If an obligation needs a facility unavailable under this worker, use another admitted Linux environment or leave that obligation blocked. Do not label WSL unsupported merely because it is virtualized, and do not label it universally equivalent to every Linux host either.

Use systemd supervision with explicit account, HOME, PATH, working directory, logging, and restart policy. Also arrange and verify how Windows starts the required WSL distribution after reboot. Microsoft documents that systemd services do not by themselves keep a WSL instance alive. Closing an observer terminal, stopping a distro, Windows sleep, Windows update/restart, and Docker Desktop restart need separate lifecycle checks.

For an owner-operated setup it is acceptable to start a qualification session while the workstation is awake and let later jobs wait when it is unavailable. Do not disable sleep, disk encryption, or Windows security settings merely to make CI look always-on. Any always-on policy is an explicit owner choice.

Tailscale's initial allow-all policy is not a substitute for deliberate access rules; VPN rules also do not automatically restrict unrelated LAN access.

8. Candidate, receipts, and resumption

Candidate record

One immutable candidate records:

  • Repository identity, commit and tree; dirty development snapshots cannot masquerade as release candidates.
  • Core/SDK/helper/component versions and compatibility relationships.
  • Source/input manifest, dependency locks, compiler/prover/runtime pins, images and resolved environment identities.
  • Gate/publisher/validator recipe hashes and support-policy hash.
  • Required platform/gate/partition inventory.
  • Caller, site, installer, and other consumer revisions where relevant.
  • Expected artifact identities, with produced digests attached through immutable result records.

A candidate ID is derived from canonical recorded inputs, not a mutable branch, latest, or a human version alone.

Gate receipt

Record candidate ID; gate and logical partition; source; worker capability/environment identity; exact command/tool versions; attempt; outcome; timestamps; output digests; and durable raw-evidence locations/digests. Record reuse explicitly with the producing receipt and the input-equivalence decision. Retain failed attempts.

Outcomes distinguish pending, running, passed, failed, cancelled, timed out, unsupported, and explicitly excluded. Required missing/unknown work is not success. A reused result is accepted only through checked identity and evidence policy, not by copying a prior green status.

State model

frozen -> qualifying -> qualified -> owner-promoted
                         |
                         +-> publishing -> partial
                                      \-> published-unverified -> complete

Publication state is per registry/package/version/digest and also aggregated for the compatible release set. Some uploads succeeding must not make the whole set complete.

Recovery rules

  • Buildbot request IDs, attempts, and durable candidate state outlive the CLI/assistant session. Observers can detach and reattach.
  • Buildbot's database stores requests/state, but its default in-memory message queue does not make every trigger durable across controller restart. Persist the candidate, obtain an acknowledged request ID, and reconcile incomplete requests after restart.
  • Restart incomplete gates at a meaningful boundary. Do not promise arbitrary subprocesses resume mid-instruction.
  • Reuse completed same-input gates; reject stale, foreign-source, duplicate, missing, or unreadable evidence.
  • A lost watcher connection is an observation error. Query the existing request before submitting a replacement.
  • Before retrying an uncertain publication, inspect the registry. Match expected source/package bytes or an explicitly defined equivalent package identity; already exists alone proves nothing.
  • Retry transport/rate-limit/index-propagation conditions under a bounded policy. Authentication, compilation, version, and digest failures require correction, not blind retries.
  • Never move an existing release tag or replace an existing package to recover a run.

  • Migrate installer/updater/helper endpoint resolution to the owner channel where needed. Do not assume current hard-coded public URLs already support private bundles. Preserve digest/trust checks; a test-only mirror override is not proof of default production bootstrap.
  • Validate the compatible core/SDK/helper set before changing the channel pointer.
  • Keep the prior installed build usable on failed verification/promotion. Application data rollback remains governed by the project's actual compatibility rules, not by a generic promise to downgrade binaries safely.

Public publication is optional but not approximate:

  1. Non-publishing preflight uses the actual working directories, relative arguments, output ownership/layouts, package contents, and native dependency/SBOM checks.
  2. Qualify/promote the same bytes where possible. If a tool repackages/rebuilds on upload, retain inputs and verify the uploaded package against the qualified expected identity; do not assert equality without checking it.
  3. Publish according to a validated dependency DAG with per-package receipts.
  4. Retrieve actual registry packages/native assets and exercise real installation/default provisioning. Local package success is not registry-install success.
  5. Advance compatible consumer pins, site/tap/catalog promotion, and public completion status only after their required verification. Partial publication remains visible and resumable.

Trust policy

Gripsack 0053 records a policy tied to authorized GitHub-hosted release provenance. Leaving Actions requires an explicit verifier/signing-policy migration.

Use an owner-authorized signing identity whose private key is unavailable to general build workers, and pin the verification key/policy on consuming machines. Bind repository, source, recipe/policy, artifacts, and acceptance evidence. Signing authenticates the authorized producer/approval; it is not an independent theorem that compilation was correct.

Do not route self-built artifacts through an Actions signing job to imply GitHub-hosted compilation. Update installers/verifiers, examples, negative tests, and published trust claims together. Old signatures and published packages remain immutable history.

11. Storage, security, and operations

  • The controller is an execution authority. Protect its configuration, worker credentials, request permissions, and administrative endpoints. Project code is executed on workers, not imported as arbitrary controller configuration.
  • Workers have no release-signing key, registry publish token, personal browser/keychain profile, personal SSH agent, or unrelated production access.
  • Use fresh workspaces/private fixture homes and scoped artifact-upload credentials. Docker-socket access and raw native shell execution require an explicit trusted-worker boundary.
  • Do not expose public fork builds to persistent owner hardware. Future external contributions need a separate disposable/untrusted execution pool and cache scope.
  • Retain promoted artifacts/manifests/acceptance evidence for the release's supported lifetime. Start with 30–90 days for non-promoted attempt logs, plus enough failure history for investigation.
  • Cache eviction must never delete the only copy of a qualified artifact or acceptance receipt. Logs/prover caches/traces do not belong in source control.
  • Keep at least one durable copy of promoted bundles and controller backups outside the CI worker's writable storage/failure domain. A mounted writable backup is not independent protection.
  • Test restore, not just backup creation. A single-controller service is acceptable initially; do not introduce a cluster merely to avoid a documented restore procedure.
  • Minimum tool versions, clock/timestamp handling, output UID/GID, output directory creation, available disk, and resource budgets belong in preflight. Never broad-chown/chmod the owner's repository or HOME to repair an output mount.

"""Validate handover consistency. This does not test a Cadence implementation."""
from __future__ import annotations

from collections import Counter
from fractions import Fraction
import hashlib
import json
from pathlib import Path
import re
import tomllib

ROOT = Path(__file__).resolve().parents[1]
REQUEST_OPERATIONS = {"hello", "key", "text", "advance", "resize", "action",
                      "barrier", "snapshot", "capture", "deliver", "quit"}
EXPECTED_CLAIMS = {*(f"VP-{n:02d}" for n in range(1, 6)),
                   *(f"VK-{n:02d}" for n in range(1, 7)), "VL-01", "VR-01"}


def digest(path: Path) -> str:
    return hashlib.sha256(path.read_bytes()).hexdigest()


def require(condition: bool, message: str) -> None:
    if not condition:
        raise SystemExit(message)


def json_file(relative: str):
    return json.loads((ROOT / relative).read_text())


def check_fixtures() -> int:
    data = json_file("fixtures/scoring.json")
    for case in data["cases"]:
        target, typed, first = case["target"], [], {}
        attempts = correct_attempts = deletions = overflows = 0
        dirty = False
        for event in case["events"]:
            if event == "Backspace":
                if typed:
                    typed.pop()
                    deletions += 1
                    dirty = True
                continue
            position = len(typed)
            attempts += 1
            correct = position < len(target) and event == target[position]
            correct_attempts += int(correct)
            dirty |= not correct
            if position < len(target):
                first.setdefault(position, correct)
            else:
                overflows += 1
            typed.append(event)
        visible = sum(character == target[index]
                      for index, character in enumerate(typed) if index < len(target))
        actual = {"first_correct": sum(first.values()), "first_attempted": len(first),
                  "correct_attempts": correct_attempts, "content_attempts": attempts,
                  "deletions": deletions, "overflow_attempts": overflows,
                  "correct_visible_units": visible,
                  "clean_completion": ("".join(typed) == target and not dirty
                                       and not case["interrupted"]),
                  "measurement_uninterrupted": not case["interrupted"]}
        expected = case["expected"]
        for key, value in actual.items():
            require(value == expected[key], f"{case['id']}: {key}: {value} != {expected[key]}")
        active = case["active_microseconds"]
        ratio = Fraction(visible * 60_000_000, 5 * active) if active else None
        supplied = expected["correct_wpm_fraction"]
        require(ratio == (Fraction(*supplied) if supplied else None),
                f"{case['id']}: WPM fraction mismatch")
        if "numeric_expected" in case:
            numeric = case["numeric_expected"]
            digits = sum(c.isascii() and c.isdigit() and c == target[i]
                         for i, c in enumerate(typed) if i < len(target))
            require(digits == numeric["correct_digits"], "Numeric digit count mismatch")
            require(Fraction(digits * 60_000_000, active)
                    == Fraction(*numeric["digits_per_minute_fraction"]),
                    "Numeric throughput mismatch")
    timing = data["timing_case"]
    paused = sum(end - start for start, end in timing["pauses"])
    require(timing["elapsed_microseconds"] - paused == timing["expected_active_microseconds"],
            "Pause arithmetic mismatch")
    return len(data["cases"])

    for path in ROOT.rglob("*.json"):

    defaults = tomllib.loads((ROOT / "config/defaults.toml").read_text())

"""Check the handover's bounded TLA models, not the future implementation."""

import hashlib
import json
import os
from pathlib import Path
import re
import subprocess
import tempfile

ROOT = Path(__file__).resolve().parents[1]
EXPECTED_TOOL_SHA256 = "936a262061c914694dfd669a543be24573c45d5aa0ff20a8b96b23d01e050e88"
TOOL_ENV = "TLA2TOOLS_JAR"
MODEL_TIMEOUT_SECONDS = 60
CASES = [
    ("AsyncAdmission", "AsyncAdmission.cfg", None),
    ("DurableCheckpoint", "DurableCheckpoint.cfg", None),
    ("CausalBarrier", "CausalBarrier.cfg", None),
    ("AsyncAdmission", "AsyncAdmission-no-epoch.cfg", "AcceptedFresh"),
    ("AsyncAdmission", "AsyncAdmission-no-pending.cfg", "AtMostOnce"),

    ("CausalBarrier", "CausalBarrier-early-return.cfg", "NoEarlyReturn"),
]


def sha256(path: Path) -> str:
    return hashlib.sha256(path.read_bytes()).hexdigest()


def main() -> None:
    supplied = os.environ.get(TOOL_ENV)
    if not supplied:
        raise SystemExit(f"Set {TOOL_ENV} to the checksum-verified TLC 1.7.4 jar")
    jar = Path(supplied).resolve(strict=True)
    if sha256(jar) != EXPECTED_TOOL_SHA256:
        raise SystemExit("TLC tool digest mismatch; no checks executed")
    output = ROOT / "evidence" / "model-checks"
    output.mkdir(parents=True, exist_ok=True)
    results = []
    for module, config, expected_fault in CASES:
        with tempfile.TemporaryDirectory(prefix="cadence-tlc-") as temporary:
            command = ["java", "-XX:+UseParallelGC", "-Xmx256m", "-cp", str(jar),
                       "tlc2.TLC", "-workers", "1", "-config", config,
                       "-metadir", temporary, module]
            try:
                run = subprocess.run(command, cwd=ROOT / "formal", text=True,
                                     stdout=subprocess.PIPE, stderr=subprocess.STDOUT,
                                     timeout=MODEL_TIMEOUT_SECONDS, check=False)
            except subprocess.TimeoutExpired as error:
                raise SystemExit(f"{config}: timed out; this is not a fault kill") from error
        log = run.stdout
        (output / f"{config}.log").write_text(log, encoding="utf-8")
        if expected_fault is None:
            passed = run.returncode == 0 and "No error has been found" in log
        else:
            passed = (run.returncode != 0
                      and f"Invariant {expected_fault} is violated" in log
                      and "State 1:" in log)
        counts = re.search(r"(\d+) states generated, (\d+) distinct states found", log)
        result = {"module": module, "config": config, "expected_fault": expected_fault,
                  "passed": passed, "return_code": run.returncode,
                  "model_sha256": sha256(ROOT / "formal" / f"{module}.tla"),
                  "config_sha256": sha256(ROOT / "formal" / config),
                  "log_sha256": sha256(output / f"{config}.log"),
                  "states_generated": int(counts[1]) if counts else None,
                  "distinct_states": int(counts[2]) if counts else None}
        results.append(result)
        print(config, "PASS" if passed else "FAIL", result["distinct_states"])
        if not passed:
            print(log[-7000:])
            break
    report = {"scope": "bounded abstract design checks only",
              "tool": "TLC 1.7.4", "tool_sha256": EXPECTED_TOOL_SHA256,
              "all_passed": len(results) == len(CASES) and all(r["passed"] for r in results),
              "cases": results}
    (ROOT / "evidence" / "tla-results.json").write_text(json.dumps(report, indent=2) + "\n")
    if not report["all_passed"]:
        raise SystemExit(1)


if __name__ == "__main__":
    main()
